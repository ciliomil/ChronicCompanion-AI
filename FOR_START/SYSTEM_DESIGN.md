# SYSTEM_DESIGN.md

## 1. 系统定位
本系统是一个面向糖尿病老年用户陪伴场景的科研原型，目标是验证“三层长期记忆机制”是否能够提升个性化聊天与温和建议效果。

系统重点不是做复杂产品功能，而是围绕以下主线展开：
- 记忆组织
- 记忆更新
- 记忆检索
- 回答生成
- 安全控制

---

## 2. 总体架构
系统由以下核心模块组成：

- 对话管理模块
- 三层记忆存储模块
- 记忆更新模块
- 需求推测与检索模块
- 回答生成模块
- 安全控制模块

推荐的调用流程为：

1. 接收用户输入
2. 进行风险初判
3. 基于 query 和画像做需求推测
4. 从中层记忆检索相关事件与需求-方案轨迹
5. 必要时回到底层原始交互补充证据
6. 组织上下文并调用 LLM 生成回答
7. 将本轮对话写入底层
8. 从本轮对话增量抽取中层条目
9. 在周期性时机更新顶层画像

---

## 3. 三层记忆结构

### 3.1 底层：原始交互层
作用：
- 保存原始对话文本
- 保留可回溯证据
- 为中层抽取和最终回答提供原始依据

建议内容：
- session_id
- turn_id
- role
- text
- timestamp
- topic_id / chunk_id

说明：
- 底层不做复杂抽象
- 只做简单编号、分块和存储
- 分块粒度可先按 topic 或一段连续交互实现

### 3.2 中层：用户记忆层
中层比底层更贴近“用户理解”，建议分为两个核心模块。

#### A. 事件列表
作用：
- 记录用户在现实生活或慢病管理过程中的重要事件
- 强调时间信息和事件脉络

建议区分：
- 就诊相关事件
- 生活相关事件

建议字段：
- event_id
- event_type
- timestamp
- source_turn_ids
- event_summary
- tags

#### B. 需求-方案列表
作用：
- 记录某一阶段中的隐含需求、AI 应对方式与用户反馈
- 保留“需求—解决方式—反馈”的轨迹

建议字段：
- item_id
- timestamp
- source_turn_ids
- inferred_need
- ai_solution_summary
- user_feedback_summary
- quality_score
- related_tags

说明：
- 中层是后续需求检索和偏好归纳的核心
- 比单纯保存历史对话更适合做个性化服务支撑

### 3.3 顶层：用户画像层
顶层用于形成较稳定但可持续更新的用户画像，建议包括三部分。

#### A. 用户基本背景信息
建议包括：
- 姓名
- 年龄
- 病史
- 生活习惯
- 家庭关系
- 主要爱好

建议形式：
- 一个结构化字典对象

#### B. 近期状态
建议包括：
- 身体状态
- 家庭状态
- 兴趣变化

建议形式：
- 一个结构化对象
- 身体状态与家庭状态可先用描述性文本
- 兴趣变化可用集合 / 列表表达

#### C. 主要需求及其偏好结构
作用：
- 表达系统长期识别出的核心需求类型
- 为每类需求保留较具代表性的偏好倾向

建议形式：
- 树状或层级结构
- 第一层：主要需求
- 第二层：对应偏好
- 第三层：偏好与代表性需求-方案条目的映射

说明：
- 顶层不追求保留全部细节
- 更关注“为需求推测和个性化生成提供高层用户理解”

## 4. 记忆更新机制

### 4.1 总体原则
采用：
- 底层持续累积
- 中层随交互增量更新
- 顶层周期性归纳更新

### 4.2 底层更新
每次对话后：
- 写入原始交互文本
- 完成编号、时间戳记录、必要分块

### 4.3 中层更新
从新增交互中抽取：
- 关键事件
- 需求-方案条目

目标：
- 保留用户生活 / 就诊过程中的重要事件
- 保留用户需求、AI 解决方式、用户反馈轨迹

### 4.4 顶层更新
顶层不在每轮都强行更新，而是周期性归纳。

更新思路：
- **主要需求**：从需求-方案列表中聚合得到
- **偏好结构**：从对应需求下的用户反馈逐步提炼
- **近期状态**：从时间上较近的事件中总结得到
- **基本背景信息**：保守更新，仅在新信息明确且具有稳定性时修订

原则：
- 避免频繁波动造成画像失真
- 保持顶层稳定性与中层时效性之间的平衡

---

## 5. 记忆检索机制

### 5.1 总体策略
不直接对全部历史做 query 相似度匹配，而采用：
1. 先推测当前需求
2. 再分层检索相关历史
3. 必要时补充底层证据
4. 最后生成回答

### 5.2 需求推测
输入：
- 当前 query
- 用户基本背景信息
- 近期状态
- 顶层主要需求

输出：
- 当前最可能需求
- 可选的次级候选需求

作用：
- 为后续检索定方向
- 减少“语义相似但实际无用”的召回

### 5.3 中层检索
围绕当前需求，从中层优先检索：
- 相关需求-方案轨迹
- 该需求下更有代表性的偏好线索
- 必要时补充关联事件

### 5.4 底层补证
当中层信息过于摘要或缺少细节时：
- 回到底层原始交互层查找对应 turn
- 补充原始证据给生成模块

---

## 6. 回答生成机制
回答生成阶段的输入建议包括：
- 当前 query
- 顶层画像信息
- 相关需求-方案轨迹
- 必要的底层原始证据
- 安全约束结果

目标：
- 回答体现个性化
- 回答与近期状态、历史偏好相匹配
- 回答不越过医疗安全边界

---

## 7. 安全控制设计
系统需要区分：
- 低风险：健康教育、通俗解释、生活方式建议
- 中风险：带个体情况的提醒或温和建议
- 高风险：诊断判断、治疗替代、药量调整等
- 紧急风险：疑似急症或明显危险情况

安全模块建议独立实现，避免散落在聊天逻辑中。
